# Full-game application runtime

`src/main.ts` mounts one `GameApplication`; this remains the existing composition root for the campaign director and IndexedDB repository, fixed-step `CombatEngine`, native-asset `GameRenderer`, DOM UI, `RuntimeInput`, and `StoryPresentation`. `GameApplication` owns the single requestAnimationFrame scheduler.

Combat advances at 60 Hz with a maximum of five catch-up steps. The frame loop rechecks the current screen after every simulation tick and stops the batch immediately when a tick opens pause, map, journal, companion, choice, or another blocking screen. It does not continue combat catch-up behind a modal. Persisted `pagehide` clears input, pauses an active game, and cancels the scheduler; `pageshow` resets frame timing and schedules it once. Non-persisted `pagehide` disposes listeners, UI, previews, renderer, presentation, input, and the save connection. World-operation and lifecycle generations prevent stale asynchronous loads, durable events, or previews from committing into a replaced run or disposed application.

New Game, Continue, explicit slot Load, Import, Export, save creation, and Travel route through the current campaign/storage APIs. Continue/Load retries retain the selected slot; import and travel retries retain their payload/route. On durable-event commit failure, the exact event and idempotency key remain queued while the app blocks menus, gameplay, save/import/export, checkpoints, and ending choices behind a full-screen error. Retry reprocesses that same event, syncs committed facts once, then resumes gameplay. Replacing the world waits for the serialized old-run event drain and reconstructs from committed facts without allowing stale loads to replace the run. Menu close returns to the opening screen, including Settings opened from Title.

Input bindings use explicit independent keyboard and gamepad maps (`InputBindingMaps`); browser key values and one-based `Gamepad Button N` values are not mixed, and neither device has a hidden fallback after remapping. New settings start from `DEFAULT_INPUT_BINDINGS`. Stored maps are authoritative, including deliberately empty entries; the one-time storage migration preserves legacy effective controls. `RuntimeInput` buffers discrete keyboard edges between fixed samples, preserves Heavy press/held/release semantics, uses the mapped directional actions for command-wheel selection, and prevents browser defaults for mapped keyboard inputs. Its scoped Chromium QA record is [evidence/application/input-behavior-2026-09-30.json](../../evidence/application/input-behavior-2026-09-30.json). That record covers keyboard-driven input and a synthetic gamepad only; it does not claim hardware gamepad, real blur/hide, or BFCache exercise.

Native companion abilities are projected from the engine roster and dispatched through the assigned companion's engine command; absence, cooldown, token, target, and Dominion/Bond gates remain engine-owned. Action-gated world interactions are not resolved by marker clicks: authored actor identities must resolve uniquely, and prompts carry exact placement IDs. The movable `camp-loose-snare` uses its `CombatSnapshot.movableObjects` pose for prompt location; its Koro utility-special path dispatches through `commandCompanion`, while the authored staff-heavy fallback uses the engine's Heavy-impact interaction path. App forwards the resulting `object-moved` event through the durable CampaignDirector queue and passes committed facts to the engine; the existing RAF forwards the complete CombatSnapshot to the renderer. App does not invent movement facts or run a local object tween. Marked actions display mapped controls and never use generic E. Companion previews require the exact manifest asset and `${companionId}:idle` action; the existing application RAF advances their handles only while the companion screen is active, and host removal/screen exit/disposal releases them.

Runtime assets are read from `/assets/manifest.json` and must be the normalized producer manifest. Every required region recipe, placed prop, actor, and Orun variant must exist and be verified; native entries require explicit runtime URLs and immutable output hashes. Missing files, blocked evidence, hash mismatches, and invalid manifests produce a visible non-retryable `asset-unavailable` error with Return to Title, Load, Settings, and Save recovery choices as available; transient transport failures remain retryable. The application never guesses asset URLs, fabricates readiness, or substitutes primitive/fake final models. Asset evidence remains authoritative in the producer manifest and release validator.

Build output includes `dist/release-compatibility.json` from the exported build, save, and campaign schema constants. The isolated `tests/input/RuntimeInput.test.ts` and `tests/app/GameApplication.test.ts` are covered by scoped checks; project-wide typecheck/build and final production-browser checks remain centralized after sibling handoffs and are not claimed here.

## Current runtime boundary

Title, Settings, and their error/recovery surfaces are independently usable, but a full gameplay region remains blocked until its exact native assets have verified evidence. Input-level behavior is documented separately from that asset gate. Physical gamepad hardware, real window blur/document-hide, BFCache navigation, and full authored campaign traversal are not claimed as exercised by the scoped input QA.
