# Full-game application runtime

`src/main.ts` mounts one `GameApplication`; this remains the existing composition root for the campaign director and IndexedDB repository, fixed-step `CombatEngine`, native-asset `GameRenderer`, DOM UI, `RuntimeInput`, and `StoryPresentation`. `GameApplication` owns the single recurring requestAnimationFrame scheduler. Mounting again on the same HTMLElement synchronously disposes the previous application before attaching the replacement, including callers of the native constructor. Disposal is idempotent and removes only that application's world/overlay nodes; a retired handle cannot erase a replacement mount.

Combat advances at 60 Hz with a maximum of five catch-up steps. The frame loop rechecks the current screen after every simulation tick and stops the batch immediately when a tick opens pause, map, journal, companion, choice, or another blocking screen. It does not continue combat catch-up behind a modal. Persisted `pagehide` clears input, pauses an active game, and cancels the scheduler once; only a persisted `pageshow` following that suspension resets frame timing and schedules one frame. Repeated or unpaired transition events cannot add recurring loops. Non-persisted `pagehide` disposes listeners, UI, previews, renderer, presentation, input, and the save connection. An IndexedDB open completing after retirement is closed rather than retained. World-operation and lifecycle generations prevent stale asynchronous loads, durable events, or previews from committing into a replaced run or disposed application.
Combat world time is explicit: overlays, title/loading/error/ending screens, and lifecycle suspension pause the `CombatSnapshot.worldClock`; normal time resumes only when gameplay resumes. RAF accumulation and discrete input edges stay unscaled, while effects and presentation consume the snapshot clock.

The same RAF renders even when no fixed simulation step was due. It retains adjacent before/after snapshots and passes the accumulator fraction to `GameRenderer.sync`, keeping actor animation and the centered camera on the same interpolated pose. Per RAF the application drives the renderer + presentation in fixed order: `GameRenderer.sync(...)` first samples the actors, environment, camera, screen-space LODs and any movable prop transforms for the current snapshot without issuing draw calls; `StoryPresentation.update(snapshot.worldClock, { position, forward, up })` then consumes the renderer's camera basis against the same authoritative world clock so socket-bound cues see the sampled pose; `GameRenderer.render()` finally issues the actual `WebGLRenderer.render(scene, camera)`. `sync` is therefore not a draw call and the previous "renders every RAF" claim refers to this sample-then-update-then-draw chain, not to `sync` drawing on its own. Simulation still advances only in fixed steps. Blocking screens, suspension, world release and explicit redraws reset render history instead of blending stale poses into resumed gameplay.

Suspension also owns transitions that finish asynchronously: an in-flight world load or event retry completing during persisted page suspension lands on Pause with gameplay input disabled and combat time paused. A programmatic Resume cannot override suspension; restoring the page restarts the scheduler but still requires explicit player Resume. Final disposal pauses combat before releasing its owned resources. Deterministic lifecycle checks do not constitute a real BFCache or physical-controller qualification; current integrated results are tracked in the remediation plan.

New Game, Continue, explicit slot Load, Import, Export, save creation, and Travel route through the current campaign/storage APIs. Continue/Load retries retain the selected slot; import and travel retries retain their payload/route. On durable-event commit failure, the exact event and idempotency key remain queued while the app blocks menus, gameplay, save/import/export, checkpoints, and ending choices behind a full-screen error. Retry reprocesses that same event, syncs committed facts once, then resumes gameplay. Replacing the world waits for the serialized old-run event drain and reconstructs from committed facts without allowing stale loads to replace the run.

Menu history records exact opening screens, including Title→Settings→Title, Error→Settings→the same Error, and Pause→Settings→Pause. Escape and Backspace use the existing `UIAction` close/resume routing: closing the root Title or root loading/error surface preserves it instead of assuming a gameplay origin. Closing a UI-local Load/Save panel redraws its current application surface. Gameplay requires a successfully prepared renderer/region matching the current campaign, with no loading/error/blocked scene; creating a campaign or initializing storage alone does not authorize the HUD or gameplay input. Preparing another world retires the previous scene resources, and Return to Title releases the renderer/presentation as well as resetting world readiness and menu history.

Map, Journal, Companions, Hub and Settings share one tab bar, so moving between them swaps the page without adding history: Escape/Back leaves the menu for the screen that opened it (Game→Map→Journal→Settings→Back returns to Game; Pause→Settings→Journal→Back returns to Pause).

The application also rejects Pause, Map, Journal, Companions, dialogue, choice and ending panel transitions without a usable initialized world, before changing the current screen or menu history. Its required `GameViewModel.canOpenWorldPanels` projects that same readiness policy: Settings remains reachable from Title/error, but its world-only toolbar controls are absent, and keyboard/gamepad world shortcuts require the capability. Stale/programmatic controls cannot bypass the controller guard. A ready world's Settings retains normal world-panel navigation. Component fixtures set this UI capability explicitly; enabling simulator/component navigation does not certify native assets or initialized production gameplay.

Rejected world-panel navigation still renders the current surface, so successful recovery-slot creation refreshes its save rows and Export availability without granting world access or changing menu history. Accepted and unchanged transitions render once as before. Rendering a suspended, unusable gameplay surface redirects through the existing Title/error fallback rather than recursively requesting a guarded Pause.

Input bindings use explicit independent keyboard and gamepad maps (`InputBindingMaps`); browser key values and one-based `Gamepad Button N` values are not mixed, and neither device has a hidden fallback after remapping. New settings start from `DEFAULT_INPUT_BINDINGS`. Stored maps are authoritative, including deliberately empty entries; the one-time storage migration preserves legacy effective controls. `RuntimeInput` buffers discrete keyboard edges between fixed samples, preserves Heavy press/held/release semantics, uses the mapped directional actions for command-wheel selection, and prevents browser defaults for mapped keyboard inputs. Its scoped Chromium QA record is [evidence/application/input-behavior-2026-09-30.json](../../evidence/application/input-behavior-2026-09-30.json). That record covers keyboard-driven input and a synthetic gamepad only; it does not claim hardware gamepad, real blur/hide, or BFCache exercise.

Native companion abilities are projected from the engine roster and dispatched through the assigned companion's engine command; absence, cooldown, token, target, and Dominion/Bond gates remain engine-owned. Action-gated world interactions are not resolved by marker clicks: authored actor identities must resolve uniquely, and prompts carry exact placement IDs. The movable `camp-loose-snare` uses its `CombatSnapshot.movableObjects` pose for prompt location; its Koro utility-special path dispatches through `commandCompanion`, while the authored staff-heavy fallback uses the engine's Heavy-impact interaction path. App forwards the resulting `object-moved` event through the durable CampaignDirector queue and passes committed facts to the engine; the existing RAF forwards the complete CombatSnapshot to the renderer. App does not invent movement facts or run a local object tween. Marked actions display mapped controls and never use generic E. Companion previews require the exact manifest asset and `${companionId}:idle` action; the existing application RAF advances their handles only while the companion screen is active, and host removal/screen exit/disposal releases them.

Verified-policy runtime assets are read from `/assets/manifest.json`, the normalized producer manifest. That policy requires verified evidence for every required recipe, prop, actor and Orun variant. The playable candidate campaign instead projects the declared regional catalogs without changing their blocked evidence. Both policies require explicit native URLs and immutable output hashes; missing files, hash mismatches and invalid manifests fail visibly rather than substituting fake geometry. Transient transport errors remain retryable. Asset evidence remains authoritative in the producer manifest and release validator.

Build output includes `dist/release-compatibility.json` from the exported build, save, and campaign schema constants. `campaignRuntimeAssets` in `vite.config.ts` also copies the declared chapter/pedestal catalogs, their referenced native GLBs, hero portraits, scene art and biome-layer JPGs into `dist/asset-source`. Raw provider downloads, provenance reports and private evidence directories are not copied.

## Player entry and browser saves

Opening `/` in development or the built static site shows Title with the playable candidate campaign selected. `SessionConfig.initialSession` returns `CANDIDATE_CHAPTERS_SESSION` (`kind: 'chapters'`, `assets: 'candidate'`, `saveScope: 'candidate-chapters'`) for every page load; only a DEV build with an `assetPlaytest` query takes the separate Trials path.

**New Game → choose one of four heroes → Begin → Prologue** is the only player story entry. The hero roster is Aren, Yara, Vesper and Sakda. Normal entry offers no map picker, no mode selector and no companion picker: the Title shows **New Game**, **Continue**, **Load Game**, **Settings** and **Credits**, and the DEV-only **Chapters (Candidate Assets)** / **Trials (Candidate Assets)** buttons appear only when `GameViewModel.session.devModes` is true, which requires a DEV build. The hero-select screen states that the journey begins in the Prologue and that the companion joins later, when the story earns them.

The run is created only on confirmation. `select-hero` becomes `new-game`; `GameApplication` calls `CampaignDirector.startChapterRun({ runId, heroId, saveScope })`. That API **refuses any companion argument** — `startChapterRun` and `startNewRun` both throw *"A new journey starts without a traveling companion; companions are earned in the story."* — so a free companion cannot be granted even by a direct API caller. A fresh run has recruited nobody: `resetRun` sets `party = {}`, and the prologue's `prologue` quest is the only active quest.

Back and Escape return to Title without changing the existing run. On `hero-select`, Escape or Backspace dispatches `return-title` for a campaign session (and `map-select` for a DEV Trials session); the hero-select footer carries the same **Back** button. `return-title` releases the world, clears the campaign, region, run id, dialogue, choice, ending and pending payloads, and returns to Title. A run that already exists is untouched by opening hero select and backing out.

Continue and Load Game read the same `wild-crown-candidate-chapter-saves` IndexedDB database (`CANDIDATE_SAVE_DATABASE_NAME`); the production-scope repository is a different database (`wild-crown-saves`) and is never touched by the player route. Earlier candidate journeys remain available.

Committed objectives, story acknowledgements and safe checkpoints autosave through the existing transactional repository. Reload the same site in the same browser profile and choose **Continue**; **Load Game** selects a particular journey. Resume uses its safe spawn/checkpoint, not the exact movement position or an unfinished combat frame. Save/Export provide explicit checkpoints/backups. Import refuses a payload from the other scope with `scope-mismatch` and changes nothing. Saves are local to the browser profile and site origin (including port); clearing site data, private browsing or browser eviction can remove them. There is no cloud/account synchronization.

Previously the default New Game entered `PRODUCTION_SESSION`, stopped at the evidence-blocked `greenwake-environment` gate and used a different save database from playable candidate journeys. The player route now explicitly selects candidate assets in both builds, retaining the persistent **NOT RELEASE-VERIFIED** banner. The verified manifest, verified-policy asset gate, hashes and release validator are unchanged; playable does not mean release-qualified.

## Earned roster, routes and older saves

Companion recruitment, temporary absence/exile and authored route requirements are **campaign authority, not presentation unlocks**. There is no second unlock ledger anywhere in the runtime: the only authorities are the committed campaign event log and the authored chapter runtime.

**Recruitment** is derived from the committed event log. `CampaignDirector.applyRelationshipAuthority` walks `RECRUITMENT_RULES` and the authored `relationshipRules` and calls `recruitCompanion` only when a rule's `requiredEvent` matches an event that was actually committed. The Act I rules in `src/content/chapters.ts` bind Vara to `tend:vara`, Koro to `encounter:encounter-koro` and Asha to `encounter:encounter-asha`, each with an authored Bond award; later-act rules bind Nyra and Solkar's Sunmane outcomes. Each rule applies once.

**Access** is `companionAccessOf` in `src/game/campaign/access.ts`, and it is the single authority for equipping, spawning, commanding, previewing and training a companion. It reads only `campaign.world.companions[id].recruited` plus the narrative constraints that remove a companion from the journey. `COMPANION_NOT_RECRUITED[id]` gives the companion's actual recruitment requirement: tend to Vara in Greenwake; cleanse Koro in Whispering Canopy; cleanse Asha in Blood Bamboo Valley; receive the Pack fragment for Sable in Moonpine Ridge; receive the Shadow fragment for Nyra in Mistveil Basin; choose Bond for Solkar in the Sunmane resolution. These immutable messages explain the existing rules; they do not recruit anyone or add an unlock ledger. `COMPANION_EXILED` says "Solkar left after your exile decision." and `COMPANION_ABSENT` says "This companion is absent from the journey." Settings, map visits and chapter number cannot grant recruitment. Exile is permanent for Solkar: the Crown council may represent Crown, but it never restores him.

**Remembered preferences are preferences only.** `GameSettings.heroCompanions` records one remembered traveling companion per hero. `assignParty` still projects the party through `projectPartyIntoRegion`, which asks the same access authority and throws before any asset loads when the companion is unearned, and `CampaignDirector.selectParty` refuses an unavailable companion with the same reason. The preference is written only after a party transaction succeeds.

**Preview eligibility is not equipment eligibility.** The ability view model projects `previewAvailable` and `previewReason` from the application's existing `companionRestriction`, the same authority that already guards native preview creation and skill-preview dispatch. Unrecruited/absent/exiled companions show that refusal instead of a permanent “Loading native character…” placeholder, and their Preview animation + VFX controls are disabled. The party panel can additionally refuse changing equipment during an encounter; that combat-only refusal must not disable an otherwise earned preview. This adds no access rule, recruitment event or persisted field. Unrecruited relationship captions no longer claim “Available now.”

**Routes** come from the authored chapter runtime. `CampaignDirector.advanceChapter` answers with `transitionGateOf`: the segment's own `exitRequirements` must be met, no required choice may be pending, the destination may be at most one chapter ahead, and the route must be discovered. A plain traversal answers with `travelGateOf`, which never advances the chapter — a hub visit and an earned revisit stay open, a future region does not. `mapRegionAccessOf` projects travel eligibility onto the World Map; `chapterActOf` shows the current region's chapter-exit requirements in the survey. A locked region stays focusable and explains itself (`ROUTE_NOT_DISCOVERED`, `REGION_NOT_UNLOCKED`, `HOLLOW_LOCKED`, `REFUGE_LOCKED`, `PENDING_CHOICE`) but never dispatches travel. `visited:<region>` is never consulted: a walked-through region is not an earned route.

**Contextual chapter exits are not local physics traversal.** In a chapter campaign, an authored cross-region exit whose unlock fact holds offers the existing E/interact prompt within 2 metres of its 3D start. Activating that current prompt queues a traversal event through the existing durable-event pipeline; `commitEvent` calls `Director.advanceChapter`, and the normal region loader uses its committed destination checkpoint. The Director still refuses an unfinished quest/required beat/choice without changing the journey. Engine-local vault/ledge/slide/swing paths remain local, and no destination, companion, position or chapter is granted by the prompt itself.

**Pending spatial pacts stay walkable.** `presentChapterStory` only presents a pending site-bound pact when that same eligible contextual interaction is current. A completed cinematic does not open a modal several metres from its required site. Approaching the site presents the existing choice; its real `resolveInteraction` option and distance guards still decide acceptance. Non-spatial choices remain automatic.

**Native geometry is part of interaction reachability.** The Canopy monkey rescue, orchard seeds and optional Seeds on the Wind targets sit on the existing eastern seed-alcove path, outside the renderer-measured tree trunk. The native tree and all collision/support geometry are unchanged. The fixed-step traversal regression reaches all three targets through that geometry; native WASD/E separately committed the two required interactions.

**Older saves** are adopted, never rewritten with invented history. `CampaignDirector.adoptedParty` narrows an adopted party's companion to what the run actually earned: the access authority decides, and an unavailable companion is dropped rather than granted. Every earned progress record — recruitment, Bond, Dominion, story flags, the Dominion ledger — is preserved. The legacy fallback path (a save with no progress checkpoint) also drops a default companion the campaign never recruited. Loading an old save therefore never manufactures a companion and never loses earned progress.

**Trial and practice completion can never satisfy a campaign gate.** A DEV Trials run and a Training Grounds run are both `replay: true`, and the Director's campaign mutations (`advanceChapter`, `reachCheckpoint`, `beginChapterEncounter`, `acceptQuest`, `trackObjective`) call `assertCampaignRun`, which throws *"Replay runs have no chapter progression."* `persistAutosave` returns early for a replay run, so neither can write a campaign slot. Earned companion selection remains available inside practice: it changes only the transient party, and the application does not save a remembered hero-companion preference for that practice selection.

## HUD groups, focus modality and the candidate banner

### Three independent collapsible HUD groups

The world HUD has exactly three independently collapsible groups — `HudGroup = 'hero' | 'objective' | 'skills'` — held in the mounted UI's local `hudGroups` record in `src/ui/GameUI.ts`. Each group keeps its own state; collapsing one never changes another.

- **Hero** (top-left): the crest, the hero's name and title, and the vitality bar stay visible when collapsed; mana and Instinct fold into the hidden body (`wc-hud-hero-body`).
- **Objective** (top-right): the quest title and the current objective stay visible when collapsed; the step position, the interaction hint, the destination arrow and the chapter label fold into `wc-hud-objective-body`.
- **Skills** (bottom): collapsed keeps a live ready count ("N of M ready"); expanded lists every card with its own key, cost and refusal reason in `wc-hud-skills-body`.

**Objective guidance names the task, its prerequisites and the authored input.** `ChapterFlow` resolves semantic targets (such as `heartroot-canopy`) through their interaction to the actual placed site; the HUD, current area-map marker and world cue share that location, including elevated Y. The expanded objective shows its authored story/spatial description and names unfinished prerequisites instead of offering an unusable action. Eligible interactions retain their `inputHint`; `controlBindingLabel` resolves the current keyboard/controller binding, so waterwheel strikes use the heavy binding (default K), restoration uses the ability binding (default Q), and ordinary interactions use Interact (default E). Only the actual contextual interaction makes the objective ready.

**World cues are localized, presentation-only fireflies.** `ObjectiveGuidanceVisual` anchors a small green/gold cluster and ground ring at the tracked task, not at the player's height. Approach uses a broken ring; ready uses a brighter double ring; blocked uses dim stationary dashes. Completing the objective advances the cue through the existing campaign projection. Reduced Motion leaves a static readable marker. Geometry and shader materials are reused; cues have no collision, lights, shadows, campaign writes or new asset dependencies, and are disposed on region replacement.

**Ambient particles do not jump with the hero.** `RegionEnvironment` projects only ground-feature focus onto authored walk surfaces, ramps and bridge decks, retaining the last supporting height across gaps. It does not sample the visual gorge under a bridge or pin elevated effects to Y=0. Sky, camera and sun focus still follow the actor. This covers Canopy, Mistveil and Moonpine features through their common owner; Grove retains its existing ground-level anchor. The separate objective marker remains at its authored target. [Native jump evidence](../../asset-source/playtests/evidence/player-feedback/jump-anchor-native-r8.json) records trusted Space before/after at the Canopy courtyard and after a real WASD ascent to the 4 m bridge: ambient anchor excursion changed from 1.178 m to zero, while actor and camera continued rising. The regression covers ground, landing, ramp, terrace, bridge, unsupported gap and descent; the full 90-test world suite and production build passed. Native jump proof here is Canopy, not a claim of physically retesting every region.

**An earned chapter route has a gathering pillar.** Once required regional objectives and the existing `chapterActOf` / `transitionGateOf` requirements (including pending choices and required story beats) are satisfied, the authored exit gets a gold light column. A forward exit takes precedence over remaining optional objectives and the HUD names the destination. Walking into the pillar does not teleport or complete the chapter: Interact at the route still uses the durable chapter-transition path. Reload derives the beacon from saved campaign authority. Trials retain their separate native Warden waystone and `StageGoal` arrival behavior.

**Guidance verification:** the built candidate campaign was exercised in a separate browser origin using an unmodified export from the coordinator's prior physically earned Canopy run: native E received the fragment, the marker advanced to Koro's pact, native Q restored the orchard, the earned exit survived reload, and native E at the pillar reached Blood Bamboo Valley. A separately labelled replay of that run's first sixteen durable events supplied an early-Canopy fixture: native E worked at Vara, the boulder and elevated vine-route marker; journal tracking of unfinished restoration named its missing requirements without offering Q or an exit. Reduced Motion kept marker uniforms static while simulation ticks advanced. These checks do not claim a new complete campaign playthrough or release asset acceptance. Evidence: `asset-source/playtests/evidence/player-feedback/quest-guidance-native-r7.json` and the `quest-guidance-*-r7.png` captures.

**The Fallen Scout uses companion controls, not another Interact site.** After tending Vara, an unequipped party gets the Companions binding (default C) and no spatial beacon; selection remains manual. Once Vara is equipped, the HUD shows the Command Wheel binding (default R) and Mark Weakness at the present, living howler. The warning step guides to the simulation's actual warned threat, or the authored howler while waiting for a warning, never to Vara's care site. Face away nearby, wait for Vara's warning, then turn toward that threat; no interaction key is required. Hidden, downed, absent or unloaded-region threats never produce a fallback placement beacon.

**Scout regression evidence:** the earlier sixteen-event replay already contained optional Greenwake mark/warning semantics and did not exercise this blocked lesson. The [separate native scout replay](../../asset-source/playtests/evidence/player-feedback/scout-block-native-r9.json) omits those two events, starts with an empty party, and uses real E care, C selection, R hold/hover/release and movement-facing input to finish all three Fallen Scout objectives. Scouting now accepts unengaged wild combatants without changing their allegiance, damaging them or enabling offensive commands/automatic support. Other chapter-route requirements are unchanged; this does not bypass locks.

Each group renders a real toggle button (`data-ui-action="hud-toggle"`, `data-hud-group="<group>"`, `data-focus-key="hud-toggle-<group>"`) carrying `aria-expanded` and `aria-controls="wc-hud-<group>-body"`, with an English accessible name. The controlled body is hidden with the `hidden` attribute when collapsed, so assistive technology reads the same state the chevron shows.

**The state is mount-local, not saved.** `hudGroups` lives in the closure of `mountGameUI`; it is included in the render signature (`gameUiSignature(next) + '|' + hudGroups.hero + '|' + hudGroups.objective + '|' + hudGroups.skills`) so a toggle forces a re-render, and it survives ordinary HUD refreshes and menu round-trips. It is never written to the save repository, the settings record or the campaign, and it does not survive a remount. All three groups start expanded.

**Collapse is presentation-only.** Toggling a group does not pause the simulation, change the camera or viewport, mutate resources or progression, or hide the only actionable cue for a required interaction: the interaction prompt and the destination panel are rendered outside the collapsed bodies.

**A pointer toggle hands the focus back to the game.** `toggleHudGroup` focuses the toggle and, when the last input modality was `pointer` and the screen is `game`, blurs it and focuses `.wc-input-host`, so the next Space is a jump rather than a re-toggle. The toggle carries `pointer-events: auto` and a 44 px minimum target, so clicking it cannot click through into an attack or a world interaction. Keyboard activation is handled on `keydown` before a cooldown redraw can replace the button, and a repeated `keydown` is ignored.

**Pause exposes the same three groups.** The Pause card — in the campaign and in Training Grounds — carries a **HUD panels** group with **Hero details**, **Objective details** and **Skill details** buttons. They drive the same mounted-local flags and the same `hud-toggle` action, and they report their state with `aria-pressed` plus a visible Expanded/Collapsed label. Main exercised D-pad focus and A activation through the application's actual RAF using a labelled standard-gamepad fixture; combat time remained paused. This proves logical navigation and ownership, not a physical gamepad. These controls add no gameplay binding, persisted preference or save field.

**Input modality is tracked, not assumed.** `GameUI` records the last device on `container.dataset.inputModality` as `pointer`, `keyboard` or `gamepad`, set on pointer down, on key down and on a gamepad button change. Keyboard and gamepad navigation use the existing D-pad/stick focus movement and the A/B buttons; the world keeps the keyboard when a pointer-driven toggle yields it.

### Candidate and verified banner policy

`bannerOf(session, showVerifiedBanner)` is the only banner authority:

- a DEV Trials session shows that map's own `LOCAL PLAYTEST · GENERATED GLB CANDIDATES · NOT RELEASE-VERIFIED · <MAP> ONLY` banner;
- a **candidate** session always shows its banner and it cannot be hidden — a candidate campaign shows `CANDIDATE CHAPTERS · GENERATED ASSETS · NOT RELEASE-VERIFIED`, and a candidate practice session shows `TRAINING GROUNDS · GENERATED ASSETS · NOT RELEASE-VERIFIED`;
- a **verified** session shows `CAMPAIGN · VERIFIED ASSETS` (or `TRAINING GROUNDS · VERIFIED ASSETS`) only when the presentation flag is on, and shows nothing otherwise.

`SHOW_VERIFIED_ASSET_BANNER` in `src/app/GameApplication.ts` is `VITE_SHOW_ASSET_BANNER === 'true'`, or the DEV default when the variable is not explicitly `'false'`. It is a **presentation flag only**: it changes the strip's visibility and nothing else. It never changes an asset's `evidenceStatus`, the candidate save isolation, the verified-policy asset gate, the hashes or the release validator. A production-mode bundle alone is not release qualification. ## Training Grounds (player practice)

Training Grounds is the player's **earned practice** activity, entered from the running campaign at a safe point. It is not a second campaign and not the DEV Trials fixture.

### Entry and the earned map list

Two entries exist in the campaign UI: the **Training Grounds** button on the Pause card and the **Training Grounds** section in the hub (the hub is available in the authored hub regions, `the-grove` and `refuge`). The hub carries the same authoritative reason as the Pause entry.

`GameApplication.trainingReason` refuses the entry and states why, in this order: not a chapter session or no campaign or already inside practice → *"Training Grounds require your campaign journey, not a DEV fixture or another practice session."*; a busy world (a pending world event, a failed world event, dialogue, a choice, an entry shot, a tutorial, a traversal, a party change, a player outcome) → *"Finish the current story, encounter, or activity before practicing."*; a screen that is not Pause, hub or the Training selector → *"Pause at a safe checkpoint or visit a sanctuary to enter Training Grounds."*. `TrainingGrounds.trainingEntryReason` then answers the part only the campaign and the live world know: a replay source is refused; an active encounter (campaign or engine), an active nursery escort or dodge practice, a downed or hidden hero, an airborne hero, a pending required story beat, an open dialogue or a pending choice are each refused with their own reason; a journey that has cleared no region story is refused with *"Clear a region story to earn Training Grounds practice."*; and the player must stand inside an authored safe checkpoint's own radius — a distant floor is not a practice spot, and a boss arena's pre-fight spawn is excluded.

`trainingMapsOf` lists the five authored practice maps — Greenwake, Whispering Canopy, The Grove, Moonpine Ridge, Mistveil Basin — in authored order. A map is unlocked exactly when the journey has **cleared that region's authored story**: every authored chapter segment of that region that carries exit requirements must have all of them met. A segment without exit requirements (a sanctuary's ordinary visit, the chapter-7 return corridors) clears nothing on its own, so a visited hub never unlocks a map and a later return journey never relocks an earned one. A locked map carries the reason the player can act on: *"Finish the <region> story to unlock <map> practice."* An optional quest never becomes a requirement, and a chapter ahead of the journey's own never opens a map early.

### The practice session

`createTrainingDirector` is the factory, and it refuses independently of the UI: an unknown map, a replay source, a locked map, an asset policy that does not match the journey's own (`"Training Grounds practice keeps the journey's own asset policy."`) and an asset policy that does not match the journey's save scope (`"Training Grounds practice keeps the journey's own save scope."`).

The practice session:

- runs under `SessionConfig` `kind: 'training'` with the **journey's own asset policy** and the map id, and **no save scope of its own** — `trainingSession(mapId, assets)` has no `saveScope` field, and `activeSaves` returns `null` for a non-chapter session, so a practice session owns no `SaveRepository` at all;
- uses a **separate Director** (`new CampaignDirector({ saveScope, chapters })` with no repository) whose `startPracticeRun` **copies the source campaign by value** (`structuredClone`), changes only the run id, and carries the traveling companion over only when the source's equipped companion is actually available under the same access authority;
- carries **no story progress**: the practice run's quest, objective, beat and choice lists are empty, and it is `replay: true`;
- keeps the journey's own **hero** (`source.session.heroId`): the Training selector offers no hero picker and no companion picker;
- uses the same authored combat stage as the corresponding playtest (`ASSET_PLAYTESTS`), including the waystone exit and the trial set.

While a practice session is active, `GameApplication.dispatch` accepts only `TRAINING_ACTIONS` — pause, resume, close-screen, open-map, open-companions, open-settings, select-companion, issue-command, use-ability, preview-companion-skill, wheel, update-settings, remap, dismiss-tutorial, reset-tutorials. Every other action is refused with *"Return to your journey to continue the story, travel, or manage campaign saves."* So a practice session cannot save, load, import, export, travel, create a save slot, start a new run, or write a campaign event: `queueEvents` returns immediately for a training session, so no world event is ever queued from it. `return-title` is not refused but redirected: while a practice session is active it is intercepted before the action filter and performs the journey return instead of leaving to Title. The practice map is read-only while it is active, the hub and journal tabs are hidden, and the HUD carries a **PRACTICE · Training Grounds · Your journey is unchanged** strip.

**What practice does not write.** A practice session writes no campaign slot, no campaign event, no recruitment, no Bond or Dominion, no restoration fact, no chapter unlock and no quest progress. The `settings` record is not campaign state: it lives in the `settings` object store, which is separate from the `slots` and `runs` stores that hold campaign progress, and it carries only presentation and binding values. A settings change during practice therefore cannot advance, unlock or alter the journey. `assignParty` additionally skips `rememberCompanion` for a training session, so a practice party choice does not even update the remembered per-hero preference.

### Return and failure isolation

`startTraining` stores a `TrainingReturnContext` — the original session, the original Director, the original snapshot and `combat.serialize()` — before the world is replaced, and the original Director is rebound on return. `leaveTraining` restores the original session, campaign, run id and hero, rebuilds the world, then hydrates the original simulation from the saved ticket (`this.combat.restore(context.combat)`) and rebinds the live collision fields to the rebuilt renderer (`setSceneColliders(renderer.getNativeSolidColliders(), renderer.getNativeSupportFields())`). The player's actual resources come back: a journey that was at 37 vitality, 24 mana and 7 Instinct before practising resumes at exactly those values, and nothing done in practice heals or refills the original.

A failed return is a **retryable, isolated** failure. If the world rebuild throws, `leaveTraining` shows the loading error with `operationId: 'training-return'`, keeps `trainingReturn` intact (the original journey and the resource ticket are not lost), and the only offered action is **Retry** — the loading screen filters its recovery actions so a `training-return` operation offers nothing but the retry. `retry-load` with `operationId: 'training-return'` re-enters `leaveTraining` and retries the same restoration.

The practice outcome screens are equally isolated: **Practice Complete** and **Practice Over** both state that the journey, its saves and its history are unchanged, and both offer only **Return to Journey** — never a new run that would escape the isolated session.

## Forest preparation progress

`GameApplication.prepareWorld` reports truthful world-loading progress to the UI through `GameViewModel.loading` (`progress`, `detail.stage`, `detail.phaseLabel`, `detail.message`) as one monotonic 0..1 value (`src/app/LoadProgress.ts`) over ordered, weighted phases, so 100% means the world is ready rather than "the GLB count finished". There is no timer: the value only moves when a phase reports real work. After the manifest is read and the region, recipe and assets are checked (`progress: 0`, stage `manifest`), the weights are: `manifest` 3, `assets` 58 (`GameRenderer.loadRegion`'s per-invocation callback, so a reused renderer cannot retain a callback closed over an old generation), `hero` 7, `world` 4 (actors, colliders, story state, audio), `waystone` 4 (playtests only), `effects` 10 (effect and trial-monster shader prewarm), `gpu` 8 (`warmGpu` and the first render) and `encounter` 6 (encounter start and trial gates). Each of the hero, world, waystone, effects and GPU phases is reported and given a paint opportunity (next frame, or 50 ms in a hidden tab) before its synchronous work starts, so the label on screen names the work actually running. Loading stays active until the encounter is prepared and the world is revealed; an encounter started outside a world preparation (for example Orun) shows an indeterminate loading state.

`GameRenderer.loadRegion` pre-counts the exact native-asset load operations its current plan performs: one count per static base batch (placements grouped by asset ID and 16 m X/Z cell), one count per *verified-and-available* LOD attempt (skipped LODs do not count toward the total), one count per movable prop, one count per authored actor instance, and one count for the fallback `actor-aren` player load when no region entity covers `aren`. The callback receives `{ completed, total, ratio }` starting at `0/total`, increments strictly as each operation completes, and reports an exact integer percentage scaled to 100 once every counted operation finishes. A recovered LOD attempt counts even when its batch is unavailable, and a required-asset failure throws before reaching 100% so the UI never reports successful completion without verified assets.

The loading screen renders the selected map's scene (`loadingSceneMarkup`): the phase label and a visible integer percentage (for example `0%` then `38%` while scene assets load), the detail line (`Loaded 3 of 8 scene assets`), and a `role="progressbar"` element with `aria-valuemin="0"`, `aria-valuemax="100"`, `aria-valuenow`, `aria-valuetext` and `aria-label="Loading progress"`. The lore line is chosen from progress (`floor(progress × loreCount)`), so it rotates deterministically without timers. When `progress` is `null` the bar is indeterminate and carries no `aria-valuenow`, so the UI never displays fabricated progress. Progress updates patch the scene in place rather than rebuilding it, so its animations do not restart. Region scenes are keyed by `GameViewModel.scene.regionId`: the selected playtest map, or for the production campaign the current region (Greenwake, Whispering Canopy, The Grove, Moonpine Ridge and Mistveil Basin have scenes; other regions use the Greenwake scene). The English in-game copy stays intact.
